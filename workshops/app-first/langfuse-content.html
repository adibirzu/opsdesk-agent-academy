The simple setup: three values, one prompt, one check.

Recommended student path: use your own Langfuse Cloud Hobby organization/project when you do not already have a reachable instance. No Docker setup is needed for that route.

  1. Choose your instance. Use your own working self-hosted installation or Langfuse Cloud. Copy the instance base URL, not a project/trace page path. It must be reachable from the app backend; a hosted builder cannot reach a Langfuse server bound only to your laptop loopback.
  2. Add three server values. Store LANGFUSE_BASE_URL, LANGFUSE_PUBLIC_KEY and LANGFUSE_SECRET_KEY in the app's backend secrets/environment settings. Never enter real keys in this static training page or a builder chat.
  3. Give the builder the integration prompt. Download the Langfuse wiring instructions (.md). One-time code instrumentation is required; the builder/coding agent does it using your existing model integration.
  4. Run one actual action. Open its exact trace in your project. Only independent readback earns a verified result.

The same three values work for a compatible self-hosted or Cloud setup. Code still needs the correct SDK/runtime integration and a reachable approved destination; the values alone do not instrument an app.

Local installation commands · review before starting

From the workshop checkout, create a new ignored private clone. This downloads source, not an entitlement or a ready-made project.

git clone https://github.com/langfuse/langfuse.git local/private/langfuse-home
cd local/private/langfuse-home
git rev-parse HEAD
docker compose config --services

Record the revision for replay. Review the compose file and official instructions: change its default secrets privately, review published ports, keep local access bound to your intended interface and verify native image/platform support. Do not paste the resolved full compose configuration into shared logs because it can contain secrets. Only after that review, start your own compose project:

docker compose up

Open its configured UI (the upstream local default is localhost:3000), sign up, create an organization/project and your own project keys. Ctrl-C stops the owned foreground stack. To stop that same project later, run docker compose stop in its directory. Do not delete volumes if you want to keep traces. Follow the recorded revision and official upgrade procedure for later changes.

2. Enable the existing Observer

The local Studio already instruments real agent work; no extra Langfuse SDK or collector daemon is needed for this path. Install the frozen studio extra. Merge the following into the existing private model TOML, replacing its telemetry table rather than adding a duplicate:

[telemetry]
enabled = true
capture_content = false
service_name = "opsdesk-agent"
langfuse_endpoint = "http://127.0.0.1:3000"
allowed_hosts = ["127.0.0.1"]
langfuse_public_key_env = "LANGFUSE_PUBLIC_KEY"
langfuse_secret_key_env = "LANGFUSE_SECRET_KEY"

This example is for a host-run Studio and host-accessible local Langfuse UI. For your own HTTPS instance, use its base URL and exact allowed host. Container-to-host addressing differs; 127.0.0.1 inside a container is that container, not your laptop. Do not weaken destination validation to make it connect.

3. Keep your project keys private

Create a private 0600 env file with only the required key names and your own values. Use an editor or private secret store; do not paste values into command history, the app browser, a public repository or this guide.

# File structure only — replace placeholders privately; do not run with these values.
LANGFUSE_PUBLIC_KEY="<YOUR_PROJECT_PUBLIC_KEY>"
LANGFUSE_SECRET_KEY="<YOUR_PROJECT_SECRET_KEY>"

4. Restart the owned app with a fresh receipt directory

chmod 600 local/private/home/studio.toml local/private/home/keys.env
PYTHONPATH=src .venv/bin/python -m agent_workshop.studio --config local/private/home/studio.toml --secrets local/private/home/keys.env --output local/private/home/observed-01 --port 8770

The file must also contain any configured model key reference required by your gateway. Stop your own previous foreground server first. Do not stop a shared listener or overwrite an old receipt folder.

5. Run one action, then inspect the three receipts

  1. Open your app/reference and run one synthetic investigation with the configured real model.
  2. Inspect the local run ID, session and trace ID, model outcome, reported tokens and exporter result.
  3. Click the exact trace readback control in that same browser session. Independently find that exact trace in your own Langfuse project.
  4. Open its observations: agent root, authorization, each actual generation and each permitted tool. A change-intent policy path should have no generation.

The existing exporter uses OTLP HTTP/protobuf at /api/public/otel/v1/traces, server-side project Basic authentication and the version-4 ingestion header. Configure the base URL only in Studio; it appends the trace path. See the official OTel integration.

What should I learn from the trace?

  • Did the model actually call the tool, and did that handler succeed?
  • Which calls consumed time and reported tokens?
  • Did the policy stop the change before inference?
  • Was telemetry delivered and independently read back, or merely recorded locally?

Metadata-only export deliberately excludes prompt/answer/tool text. It cannot explain hidden reasoning or automatically evaluate answer quality. Cost is an estimate only when usage and matching rates are known. Langfuse readback does not prove APM/log ingestion or enforce a permission.

My trace is missing

Check local recording first, then exporter status, then exact project/session/trace readback. For 401/403 diagnose the responding service and destination/auth binding without printing credentials. For an ingestion delay, perform a bounded later readback; do not rerun paid inference automatically. A healthy UI is not an ingestion check.
